## 描述

通过对现有 8 个 skill（001-1 ~ 001-6、004、005）的完整流程梳理，发现当前 Issue 闭环机制在 **流程衔接、状态管理、异常处理、知识沉淀** 四个维度存在系统性缺陷。部分缺陷已被 #15、#17 覆盖，但仍有大量底层机制问题未解决。

---

## 完整流程现状

```
001-1 issue-init   →  初始化标签（一次性）
001-2 issue        →  创建草稿 → 发布到 GitHub
001-3 issue-discuss →  拉取内容 → 讨论 → 写回评论
001-4 issue-claim  →  原子 assign + 加 in-progress 标签
001-5 issue-fix    →  检查 assignee → 创建分支
005 git-commit     →  本地提交（规范格式）
004 git-push       →  推送到远程
001-6 issue-pr     →  提 PR → 审核/合并 → 打回
```

---

## 缺陷分类

### 一、流程衔接缺陷（阶段之间断档）

| # | 缺陷 | 影响 | 当前行为 | 期望行为 |
|---|------|------|---------|---------|
| 1 | **discuss → claim 缺少"讨论结束"标记** | 讨论没达成共识就进入开发，导致返工 | discuss 写完评论即结束，无状态变更 | 增加 "共识已达成" / "方案已确定" 标记，或增加 `ready-for-claim` 标签 |
| 2 | **fix 阶段只到"创建分支"，无"解决问题完成"标记** | 开发过程黑盒，无法追踪进度 | 分支创建后流程结束 | 开发完成后显式标记（如 `ready-for-pr`），执行基础检查（lint、未提交变更检测） |
| 3 | **commit 与 issue 无强制关联** | 代码提交无法追溯到 issue | 005-git-commit 格式规范无 issue 编号要求 | commit message 中强制包含 `Refs #N` 或 `Fixes #N` |
| 4 | **PR 合并后无分支清理** | 远程/本地分支堆积 | 合并后直接结束 | 合并后自动删除远程分支，可选删除本地分支 |
| 5 | **issue 关闭后无知识沉淀** | 修复经验丢失 | close issue 即结束 | 关闭前自动/手动生成变更摘要，沉淀到 doc/otherDoc |

### 二、状态管理缺陷（标签流转不完整）

| # | 缺陷 | 影响 | 现状 | 期望 |
|---|------|------|------|------|
| 6 | **标签状态机过于简单** | 无法精确追踪 issue 生命周期 | 标签：无 → in-progress → rejected | 增加：`ready-for-claim` → `in-progress` → `ready-for-pr` → `in-review` → `resolved` / `rejected` |
| 7 | **claim 前不检查 issue 状态** | 可能 claim 已关闭/已解决的 issue | 直接执行 assign | claim 前检查 state 是否为 open，检查是否已有 `resolved` / `rejected` 标签 |
| 8 | **无 in-progress 超时释放机制** | issue 被 claim 后长期挂死 | in-progress 永久有效 | 超时 N 天无活动，自动移除 assignee 和 in-progress，发 comment 提醒 |
| 9 | **无 issue 依赖关系管理** | 并行开发时可能因依赖未就绪导致冲突 | 无依赖字段 | issue body 或标签中声明 `depends on #X`，PR 合并时检查依赖是否已解决 |

### 三、异常处理缺陷（容错能力弱）

| # | 缺陷 | 影响 | 现状 | 期望 |
|---|------|------|------|------|
| 10 | **claim 原子性验证失败后的回退策略缺失** | assign 被别人抢占后无明确下一步 | 仅输出领取结果 | 验证失败时：输出当前 assignee → 建议等待或选择其他 issue → 提供 `gh issue list --label "ready-for-claim"` |
| 11 | **Agent 异常退出后的恢复机制缺失** | 分支残留、未提交变更堆积 | 无恢复流程 | 新增 skill 或流程：检查 "orphan 分支"（in-progress 但 assignee 无近期提交）→ 自动清理或重新分配 |
| 12 | **PR 打回后的分支处理不明确** | 原分支复用还是重建？ | 打回后重新走 claim → fix → pr | 明确规则：打回后保留分支继续修改，或删除后重建；更新分支名避免混淆 |
| 13 | **fix 阶段 main 分支更新后无 rebase 机制** | PR 时可能产生大量冲突 | 从 main 创建分支后不再同步 | 定期提醒或强制要求：提 PR 前执行 `git rebase main` |
| 14 | **本地草稿与 GitHub Issue 双向同步缺失** | 本地草稿发布后，GitHub 上的修改不同步到本地 | 发布后本地文件仅追加发布记录 | 可选：定期 `gh issue view` 同步标题、标签、状态到本地草稿 |

### 四、协作与质量缺陷

| # | 缺陷 | 影响 | 现状 | 期望 |
|---|------|------|------|------|
| 15 | **无 reviewer 分配机制** | PR 提完后无人 review | 001-6-issue-pr 无 reviewer 步骤 | 提 PR 时通过 `--reviewer` 指定，或维护轮询表 |
| 16 | **无 issue 重复检测** | 可能创建重复 issue | 001-2-issue 直接创建 | 创建前 `gh issue list --search "关键词"` 提示相似 issue |
| 17 | **无 stale issue 清理机制** | 长期无活动草稿/ issue 堆积 | 无清理策略 | 超过 N 天无活动的草稿自动归档；超过 M 天无活动的 open issue 标记 `stale` |
| 18 | **discuss 阶段缺少"共识"标记** | 讨论多轮后不知道哪个方案被采纳 | 所有评论平铺 | 支持用特定 comment 格式标记 `"✅ 共识: xxx"`，或在本地记录讨论结论 |
| 19 | **无 issue 迭代/里程碑规划** | 所有 issue 平铺，无法按版本规划 | 无 milestone 概念 | 可选：按 `P0/P1/P2/P3` 标签分批，或关联 milestone |
| 20 | **无变更摘要自动生成** | 关闭 issue 时无统一格式总结 | 直接 close | close 时生成：问题根因、解决方案、涉及文件、影响范围 |

**最紧急的 Top 5 缺陷**：
1. **#2 fix 无完成标记** → 导致开发黑盒（已被 #15 部分覆盖，但需落地）
2. **#4 PR 合并无分支清理** → 技术债务快速累积

5. **#12 PR 打回分支处理不明** → 打回后操作混乱

## 建议改进路线

### 短期（立即）
- 修复 #4：在 001-6-issue-pr merge 后增加 `git push origin --delete <branch>` 和 `git branch -d <branch>`
- 修复 #10：在 001-4-issue-claim 中，验证失败时输出明确的回退指引
- 修复 #3：在 005-git-commit / 004-git-push 中，检测当前分支名是否含 `issue-<N>`，自动在 commit body 追加 `Refs #N`

### 中期（本轮迭代）
- 修复 #2、#6：配合 #15 落地 fix 阶段拆分和标签状态机完善
- 修复 #12：在 001-6-issue-pr 打回流程中明确分支处理规则
- 修复 #13：在 001-6-issue-pr 提 PR 前增加 rebase 检查

### 长期（后续迭代）
- 修复 #5、#20：新增 issue 关闭后的知识沉淀 skill
- 修复 #11：新增 Agent 异常恢复/孤儿分支清理机制
