# 代码审查（Code Review）指南

> **创建时间：** 2026-05-24  
> **所属模块：** codeDev / 代码审查  
> **简述：** 详解代码审查的目的、流程、Checklist、审查技巧，以及如何在GitHub PR中进行高效的Code Review。

---

## 一、什么是代码审查？

**代码审查（Code Review）** 是指开发者在代码合并到主干之前，由其他开发者对代码进行系统性检查的过程。

### 代码审查的核心价值

| 价值 | 说明 |
|------|------|
| **发现Bug** | 在代码上线前发现逻辑错误和边界情况 |
| **知识共享** | 团队成员互相学习，传播最佳实践 |
| **保持一致性** | 确保代码风格、设计模式统一 |
| **提升质量** | 促使开发者写出更高质量的代码 |
| **安全合规** | 发现安全隐患和合规问题 |

---

## 二、审查流程

### 2.1 开发者（PR作者）

```
1. 完成开发 → 本地通过所有检查（Linter/测试/覆盖率）
2. 按规范提交PR → 填写清晰的PR描述
3. 自审代码 → 在GitHub上逐行review自己的代码
4. 指派Reviewer → 选择2+名相关领域开发者
5. 响应评论 → 及时回复、修改、re-request review
```

### 2.2 审查者（Reviewer）

```
1. 理解变更 → 阅读PR描述和关联Issue
2. 审查代码 → 按Checklist逐项检查
3. 提出问题 → 使用GitHub评论和Suggest功能
4. 验证修改 → 确认作者已解决问题
5. 批准或拒绝 → Approve / Request changes
```

## 三、审查Checklist

### 3.1 功能正确性

- [ ] **代码是否实现了PR描述中的功能？**
- [ ] **边界条件是否处理？**（空值、越界、并发）
- [ ] **错误处理是否完善？**（不要忽略error返回值）
- [ ] **是否存在竞态条件？**（goroutine、共享状态）
- [ ] **是否有潜在的死锁或资源泄露？**

### 3.2 测试质量

- [ ] **单元测试是否覆盖所有分支？**
- [ ] **集成测试是否验证模块协作？**
- [ ] **覆盖率是否 ≥95%？**（查看CI报告）
- [ ] **测试是否独立？**（不依赖执行顺序）
- [ ] **Mock是否合理？**（不过度Mock，不Mock被测逻辑）
- [ ] **测试命名是否清晰？**（`TestXxx_场景_预期结果`）

### 3.3 代码质量

- [ ] **命名是否清晰、一致？**（函数名见名知意）
- [ ] **函数是否过长？**（建议 ≤50行，圈复杂度 ≤15）
- [ ] **是否有重复代码？**（DRY原则）
- [ ] **错误信息是否有意义？**（便于排查问题）
- [ ] **日志是否适当？**（不过多、不过少）
- [ ] **注释是否必要且准确？**（解释Why而非What）

### 3.4 安全性

- [ ] **是否有SQL注入风险？**（使用参数化查询）
- [ ] **是否有敏感信息泄露？**（密码、Token不应硬编码）
- [ ] **输入是否经过校验？**（防止注入和越界）
- [ ] **权限检查是否到位？**

### 3.5 性能

- [ ] **是否存在明显的性能问题？**（如N+1查询）
- [ ] **资源是否正确释放？**（文件、连接、锁）
- [ ] **大对象是否被不必要复制？**

### 3.6 设计

- [ ] **是否符合项目架构规范？**
- [ ] **接口设计是否合理？**（职责单一）
- [ ] **依赖关系是否清晰？**（避免循环依赖）
- [ ] **是否引入了不必要的依赖？**

## 四、GitHub PR 审查技巧

### 4.1 评论等级

| 类型 | 用法 | 示例 |
|------|------|------|
| **Approve** | 代码可以合并 | "LGTM!" |
| **Comment** | 有疑问但不阻塞 | "这里为什么这样设计？" |
| **Request changes** | 必须修改才能合并 | "这个边界条件没处理" |

### 4.2 有效评论的原则

**✅ 好的评论：**
- "这个函数超过50行了，建议拆分成两个函数"
- "这里的error被忽略了，请处理或显式注释原因"
- "建议用表格驱动测试，这样新增用例更方便"
- "这个变量名 `x` 不够清晰，建议用 `retryCount`"

**❌ 差的评论：**
- "不好"（没有说明原因和改进建议）
- "改一下"（不具体）
- "这谁写的"（人身攻击）

### 4.3 使用 Suggestion 功能

GitHub支持直接建议修改：

```diff
-    x := 0
+    retryCount := 0
```

作者可以一键接受建议，提高审查效率。

## 五、测试审查专项

作为PR审查的一部分，必须对测试代码进行严格审查：

### 5.1 单元测试审查要点

```markdown
## 审查者检查项

### 单元测试
- [ ] 每个被测函数都有对应的测试
- [ ] 测试覆盖了正常路径和异常路径
- [ ] 使用了表格驱动测试
- [ ] Mock了外部依赖
- [ ] 使用了 testify assert/require
- [ ] 测试命名清晰（TestXxx_场景_预期）

### 集成测试
- [ ] 使用了 `//go:build integration` 标记
- [ ] 使用了真实依赖（数据库、缓存）
- [ ] 测试数据准备和清理完善
- [ ] 不依赖执行顺序

### 覆盖率
- [ ] CI报告显示覆盖率 ≥95%
- [ ] 核心逻辑分支全部覆盖
- [ ] 错误处理路径有测试
```

### 5.2 测试代码也是代码

> 测试代码的质量与生产代码同等重要！

- 测试代码也需要可读性和可维护性
- 避免过度复杂的测试逻辑
- 测试辅助函数也要被测试或审查
- 不要为凑覆盖率写无意义的测试

## 六、审查时间分配

| PR大小 | 建议审查时间 | 策略 |
|--------|-------------|------|
| < 50行 | 5-10分钟 | 快速浏览，关注核心逻辑 |
| 50-200行 | 15-20分钟 | 逐行审查 |
| 200-400行 | 30-40分钟 | 分块审查，要求作者拆分 |
| > 400行 | 拒绝审查 | 要求拆分为多个小PR |

## 七、团队审查文化

### 7.1 审查原则

1. **对事不对人** — 评论对象是代码，不是作者
2. **及时响应** — 24小时内完成首次审查
3. **小步快跑** — 鼓励小而精的PR
4. **知识传递** — 审查是双向学习的过程
5. **不追求完美** — 区分"必须改"和"建议改"

### 7.2 审查者Checklist

```markdown
## PR审查记录

**PR:** #xxx
**作者:** @xxx
**审查者:** @xxx
**日期:** 2026-05-24

### 功能审查
- [ ] 功能符合需求
- [ ] 边界条件处理
- [ ] 错误处理完善

### 测试审查
- [ ] 单元测试充分
- [ ] 集成测试完善
- [ ] 覆盖率 ≥95%

### 代码质量
- [ ] 命名规范
- [ ] 无重复代码
- [ ] 圈复杂度合理

### 安全性
- [ ] 无注入风险
- [ ] 无敏感信息泄露

**结论:** Approve / Request changes / Comment
```

## 八、Checklist

- [ ] 收到PR后24小时内开始审查
- [ ] 按Checklist逐项检查
- [ ] 测试代码与生产代码同等重视
- [ ] 使用GitHub Suggest功能提高效率
- [ ] 区分"必须修改"和"建议优化"
- [ ] 审查通过后及时Approve
- [ ] 拒绝超大PR，要求拆分
- [ ] 保持礼貌和建设性态度
