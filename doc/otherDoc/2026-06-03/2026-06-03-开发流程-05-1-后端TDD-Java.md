# 单项目开发流程 — 后端 TDD（Test Driven Development）

> 文档日期：2026-06-03
> 所属系列：单项目开发完整流程
> 阶段定位：根据后端 BDD 写 Java/SpringBoot 单元测试，通过测试驱动代码实现

---

## 一、核心目标

- 从后端 BDD 场景生成 Java 单元测试
- 通过 Red-Green-Refactor 循环驱动代码实现
- 保证所有服务层和数据库逻辑符合后端 BDD
- 遵循 SpringBoot 测试规范

---

## 二、阶段职责

### 本阶段负责（约束）

- 从后端 BDD 场景生成可执行的 Java 单元测试
- 编写最小实现让测试通过
- 重构实现代码，保证测试仍通过
- 覆盖 Domain、Application、Infrastructure、API 四个层级

### 本阶段不负责（约束）

- 后端 BDD 场景编写 → 后端 BDD 阶段
- 接口契约定义 → API 契约阶段
- 前端组件开发 → 前端 CDD 阶段
- 集成测试、端到端测试 → 联调阶段

---

## 三、测试发现规则

测试用例的发现遵循以下规则。每条规则引导一个思考方向，规则之间不互斥。

### 规则 1：后端 BDD 场景映射

每条后端 BDD 场景描述了功能接口在特定数据前提下的行为，TDD 需要为每条场景编写至少一个测试方法。一个 BDD 场景可能涉及多个测试层级，每个层级各写一个测试。

映射方式：
- BDD 的数据前提 → 测试的 Given（@BeforeEach 或测试方法内的数据构造）
- BDD 的功能接口调用 → 测试的 When（调用被测方法）
- BDD 的预期结果 → 测试的 Then（assertThat 断言）

### 规则 2：分层驱动

后端 BDD 场景不直接告诉测试应该写在哪个层级。需要从场景内容判断：

| 场景关注点 | 测试层级 | SpringBoot 测试注解 |
|---|---|---|
| 领域规则、状态变更、值对象 | Domain 层 | 纯 JUnit 5，无 Spring 上下文 |
| 用例编排、事务、权限校验 | Application 层 | @ExtendWith(MockitoExtension.class) |
| 数据库操作、外部调用 | Infrastructure 层 | @DataJpaTest / @Import |
| HTTP 协议、请求/响应格式 | API 层 | @WebMvcTest |

判断依据：场景验证的是纯逻辑（Domain）、服务编排（Application）、数据存取（Infrastructure）还是 HTTP 交互（API）。

### 规则 3：SpringBoot 规范约束（强约束）

所有测试必须遵循 SpringBoot 测试规范：

**框架要求：**
- 测试框架：JUnit 5
- 断言库：AssertJ（`assertThat`）
- Mock 框架：Mockito
- Spring 测试：SpringBoot Test 系列注解

**测试命名规范：**
```java
@Test
@DisplayName("收藏文章 - 正常收藏成功")
void favoriteArticle_whenArticleExists_shouldCreateFavorite() { }
```
格式：`{方法名}_{条件}_{预期行为}`

**测试结构规范：**
```java
@Test
@DisplayName("{后端 BDD 场景名称}")
void {methodName}_{condition}_{expected}() {
    // Given — 来自后端 BDD 的数据前提
    // When  — 来自后端 BDD 的功能接口调用
    // Then  — 来自后端 BDD 的预期结果
}
```

**分层测试注解规范：**
- Domain 层：纯 JUnit 5，不启动 Spring 上下文
- Application 层：`@ExtendWith(MockitoExtension.class)`，Mock 外部依赖
- Infrastructure 层：`@DataJpaTest`（JPA）或 `@Import`（自定义 Repository）
- API 层：`@WebMvcTest(Controller.class)`，Mock Service 层

**测试配置规范：**
- 使用 `application-test.yml` 测试专用配置
- 使用 `@TestConfiguration` 定义测试专用 Bean
- 涉及数据库的测试使用 `@Transactional` 自动回滚

### 规则 4：可追溯

每个测试方法必须能追溯到后端 BDD 的某条场景。追溯方式：

- `@DisplayName` 使用后端 BDD 场景名称
- 测试类注释标注对应的功能接口和 BDD 场景编号
- 无法追溯到后端 BDD 的测试，需要说明来源（规则 6 的扩展测试）

### 规则 5：文档驱动确认（强约束）

同后端 BDD 阶段，采用**文档驱动确认**模式。

**默认流程：**

1. AI 根据后端 BDD，一次性生成测试代码
2. 代码注释中附**待确认问题**和**总结**
3. 用户在代码中批注、修改
4. AI 读取修改后继续

**主动提问的触发条件：**

- 待确认问题超过一轮未被回答
- 用户修改后测试结构不符合 SpringBoot 规范
- 发现后端 BDD 场景存在歧义，无法确定测试行为

### 规则 6：测试扩展（规则）

在编写测试过程中，如果发现后端 BDD 未覆盖的行为或边界，**直接在测试代码中补充扩展测试**。

**扩展测试的来源：**

- 实现过程中发现了新的边界条件
- Mock 行为暴露了未预料的异常路径
- 重构过程中发现了需要保护的 invariant

**扩展测试的写法：**

- `@DisplayName` 标注为"扩展测试：{原因}"
- 注释说明扩展来源
- 遵循与映射测试相同的质量标准

扩展测试在总结中单独列出数量。

## 四、Red-Green-Refactor 流程

```
1. RED      → 从后端 BDD 生成测试，测试应失败（编译通过，运行失败）
2. GREEN    → 写最小实现让测试通过
3. REFACTOR → 按项目规范整理代码，保证测试仍通过
```

**每条后端 BDD 场景对应一个完整的 Red-Green-Refactor 循环。** 不允许批量 RED 再批量 GREEN——一个场景走完一个完整循环再进入下一个。

### RED 阶段

从后端 BDD 场景生成测试方法。测试方法应编译通过但运行失败。

### GREEN 阶段

写最小实现让测试通过。**实现只需要满足对应的 TDD 测试用例**，不多做。

GREEN 阶段允许：
- 临时硬编码返回值
- 直接写在 Controller/Service 里的简单逻辑
- 不抽取任何方法或类

### REFACTOR 阶段

测试通过后，按项目规范整理代码。整理的范围：

- **目录结构** — 代码放到项目约定的包路径下（如 `controller/`、`service/`、`repository/`、`domain/`）
- **可复用资源** — 多个地方用到的枚举类、常量、工具方法，提取到公共位置
- **代码组织** — 调整类和方法的位置，符合项目的分层约定

REFACTOR 的边界：

- **不抽离无意义的方法** — 只有一两行、没有复用场景的逻辑，不需要抽成独立方法。强行抽离只会增加跳转成本，没有任何意义
- **不过度抽象** — 不为"将来可能用到"的场景提前设计接口或基类
- **目标不变** — 整理完之后，所有测试仍然通过

**判断是否需要提取的标准：** 同一段逻辑在两个以上地方出现，或者提取后可读性明显提升。不满足的不提取。

## 五、测试分层

| 层级 | 测试内容 | SpringBoot 注解 | 对应后端 BDD |
|------|---------|---|---|
| Domain 层 | 领域规则、状态变更、值对象 | 纯 JUnit 5 | 实体驱动的场景 |
| Application 层 | 用例编排、事务、权限校验 | @ExtendWith(MockitoExtension.class) | 功能接口的正向/异常场景 |
| Infrastructure 层 | 数据库操作、外部调用 | @DataJpaTest / @Import | 数据持久化场景 |
| API 层 | HTTP 协议、请求/响应格式 | @WebMvcTest | API 契约对齐后的场景 |

**分层原则：** 优先写 Domain 层测试（最快、最稳定），再写 Application 层，再写 Infrastructure 层，最后写 API 层。测试速度从快到慢，测试数量从多到少。

## 六、测试写法（规则）

### 6.1 Domain 层测试

```java
class FavoriteTest {

    @Test
    @DisplayName("收藏 - 重复收藏同一篇文章应抛出异常")
    void favorite_sameArticleTwice_shouldThrow() {
        // Given
        Article article = Article.builder().id(1L).build();
        User user = User.builder().id(1L).build();
        user.addFavorite(article);

        // When & Then
        assertThatThrownBy(() -> user.addFavorite(article))
            .isInstanceOf(AlreadyFavoritedException.class);
    }
}
```

### 6.2 Application 层测试

```java
@ExtendWith(MockitoExtension.class)
class FavoriteServiceTest {

    @Mock
    private FavoriteRepository favoriteRepository;

    @Mock
    private ArticleRepository articleRepository;

    @InjectMocks
    private FavoriteService favoriteService;

    @Test
    @DisplayName("收藏文章 - 文章不存在时应抛出异常")
    void favoriteArticle_articleNotFound_shouldThrow() {
        // Given
        when(articleRepository.findById(1L)).thenReturn(Optional.empty());

        // When & Then
        assertThatThrownBy(() -> favoriteService.favorite(1L, 1L))
            .isInstanceOf(ArticleNotFoundException.class);
    }
}
```

### 6.3 Infrastructure 层测试

```java
@DataJpaTest
@Import(FavoriteRepositoryImpl.class)
class FavoriteRepositoryTest {

    @Autowired
    private FavoriteRepository favoriteRepository;

    @Autowired
    private TestEntityManager entityManager;

    @Test
    @DisplayName("收藏查询 - 按用户ID查询收藏列表")
    void findByUserId_shouldReturnFavorites() {
        // Given
        User user = entityManager.persistAndFlush(User.builder().id(null).name("test").build());
        entityManager.persistAndFlush(Favorite.builder().userId(user.getId()).articleId(1L).build());

        // When
        List<Favorite> favorites = favoriteRepository.findByUserId(user.getId());

        // Then
        assertThat(favorites).hasSize(1);
        assertThat(favorites.get(0).getArticleId()).isEqualTo(1L);
    }
}
```

### 6.4 API 层测试

```java
@WebMvcTest(FavoriteController.class)
class FavoriteControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private FavoriteService favoriteService;

    @Test
    @DisplayName("POST /api/v1/favorites - 正常收藏成功")
    void favorite_success_shouldReturn200() throws Exception {
        // Given
        when(favoriteService.favorite(1L, 1L)).thenReturn(FavoriteResponse.success(1L));

        // When & Then
        mockMvc.perform(post("/api/v1/favorites")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"articleId\": 1}"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.success").value(true))
            .andExpect(jsonPath("$.favoriteId").value(1));
    }
}
```

### 6.5 参数化测试

```java
@ParameterizedTest(name = "收藏数量边界: {0} 篇文章 → {2}")
@CsvSource({
    "0,  false, 不存在收藏",

    "100, true,  存在100篇收藏"
})
void checkFavoriteStatus(int count, boolean expected, String description) {
    // 同一逻辑覆盖多组输入输出
}
```

## 七、测试数据管理（规则）

| 方案 | 说明 |
|------|------|
| Builder 模式 | `Entity.builder().field(value).build()` 灵活构造测试数据 |
| 测试夹具（Fixture） | `@BeforeEach` 中准备每个 Scenario 的公共数据 |
| Mock 工厂 | `mockEntity()` 方法生成符合默认值的数据，override 差异字段 |
| @Transactional | 数据库测试自动回滚，保证测试隔离 |
| @TestConfiguration | 定义测试专用 Bean，与正式配置隔离 |

## 八、测试质量（约束）

每个测试方法必须满足：

- **独立** — 不依赖其他测试的执行顺序，@BeforeEach 完成所有前提准备
- **可重复** — 多次运行结果相同，不依赖时间、随机数、外部服务
- **可追溯** — @DisplayName 对应后端 BDD 场景名称
- **单一职责** — 一个测试方法验证一个行为，不用一个测试验证多个场景
- **不测试实现细节** — 测试验证行为和结果，不验证 private 方法或内部调用链

做不到的，说明测试写的是耦合代码而非验证行为，需要重写。

---

## 九、测试完整性（约束）

每个功能接口的测试必须覆盖三种类型：

- **正向** — 正常调用成功，返回预期结果
- **异常** — 调用失败，抛出预期的异常
- **边界** — 极端条件下的行为（空值、上限、重复、并发）

三缺一，测试不完整。

## 十、输出（约束）

后端 TDD 阶段完成后必须产出以下内容：

### 测试代码

每个后端 BDD 场景对应的测试类和测试方法，遵循 SpringBoot 测试规范。

### 实现代码

通过 Red-Green-Refactor 循环产生的业务代码，所有测试通过。

### 覆盖映射

每个测试方法的 @DisplayName 对应后端 BDD 的哪条场景，无法追溯的标注来源。

### 总结

每次输出必须包含一份**总结**，供用户快速审核：

- 编写了多少个测试类、多少个测试方法
- 每个功能接口的测试覆盖情况（正向 / 异常 / 边界各多少）
- 与后端 BDD 场景的覆盖情况（是否每条都有对应）
- Red-Green-Refactor 的执行状态
- 一份快速确认检查清单

### 待确认问题

代码注释或文档中附**待确认问题清单**，每条问题包含：

- 问题描述
- 为什么需要确认（BDD 场景歧义、SpringBoot 规范不确定、Mock 行为不确定）
- 建议的默认选项

---

## 十一、完成定义（约束）

满足以下所有条件后，后端 TDD 阶段结束：

- 每条后端 BDD 场景都有对应的测试方法
- 每个测试方法都通过
- 覆盖 Domain、Application、Infrastructure、API 四个层级
- 代码经过 REFACTOR 阶段，无重复逻辑
- 所有测试遵循 SpringBoot 测试规范
- 待确认问题已全部被用户回答（或用户明确跳过）
- 总结中的检查清单已获得用户确认

---

## 十二、禁止事项（约束）

后端 TDD 阶段禁止：

- 跳过 RED 阶段直接写实现
- 为通过测试而硬编码返回值（GREEN 阶段允许临时硬编码，但 REFACTOR 阶段必须消除）
- 测试之间产生顺序依赖
- 修改测试来适配实现（测试来源是后端 BDD，实现应适配测试）
- 使用非 SpringBoot 标准的测试方式（如手动 new 上下文、使用 PowerMock 等）
- 在测试中直接操作数据库而不使用 @Transactional 回滚

## 十三、测试日志输出规范（强约束）

每次运行测试都必须留存完整日志，用于排查问题和追溯历史。

### 输出路径确认（强约束）

**AI 首次为当前项目生成测试时，必须先向用户确认：**

- 日志输出到哪个目录？默认 `.test-output/`（项目根目录下）
- 用户可指定任意路径（如 `D:/logs/my-project/tdd/`）

确认后路径写入 `.test-output/_config.json`，后续运行脚本和框架配置均读取此文件，不再重复询问。

```json
// .test-output/_config.json
{
  "tddOutputDir": ".test-output/tdd",
  "confirmedAt": "2026-06-03T140000",
  "confirmedBy": "user"
}
```

### 目录结构

```
{outputDir}/                               ← 用户确认的路径，gitignored + AI-excluded
└── tdd/
    ├── run.sh                             ← 一键运行脚本（见下方）
    ├── FavoriteServiceTest/               ← 测试类名 = 目录名
    │   ├── 2026-06-03T143000.log          ← 每次运行一份，时间戳命名，不覆盖
    │   ├── 2026-06-03T143000-summary.json
    │   ├── 2026-06-04T091500.log
    │   └── 2026-06-04T091500-summary.json
    └── _index.json                        ← 所有测试类的运行索引
```

### 日志文件说明

| 文件 | 内容 | 用途 |
|------|------|------|
| `{timestamp}.log` | 完整的测试输出（stdout + stderr） | 人读：排查失败原因 |
| `{timestamp}-summary.json` | 通过/失败/跳过数量、耗时、失败方法名 | 机器读：快速定位 |
| `_index.json` | 所有测试类的最近运行记录汇总 | 全局概览 |

`summary.json` 结构：

```json
{
  "testClass": "FavoriteServiceTest",
  "timestamp": "2026-06-03T143000",
  "total": 8,
  "passed": 7,
  "failed": 1,
  "skipped": 0,
  "durationMs": 1240,
  "failedMethods": ["favoriteArticle_articleNotFound_shouldThrow"]
}
```

### 运行脚本（强约束）

**每个测试类型的输出目录下必须有一个 `run.sh`**，用户可直接执行，不依赖 IDE。

`{outputDir}/tdd/run.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
TIMESTAMP=$(date -u +"%Y-%m-%dT%H%M%S")

# 读取配置
CONFIG_FILE="$SCRIPT_DIR/../_config.json"
if [ -f "$CONFIG_FILE" ]; then
  OUTPUT_DIR=$(python3 -c "import json; print(json.load(open('$CONFIG_FILE'))['tddOutputDir'])" 2>/dev/null || echo ".test-output/tdd")
else
  OUTPUT_DIR=".test-output/tdd"
fi

echo "=== TDD 测试运行 ${TIMESTAMP} ==="
echo "输出目录: ${OUTPUT_DIR}"
echo ""

# 运行测试，同时输出到终端和日志文件
mvn test 2>&1 | tee "${OUTPUT_DIR}/_raw-${TIMESTAMP}.log"

EXIT_CODE=${PIPESTATUS[0]}

# 整理日志（按测试类拆分）
node scripts/tdd-log-organizer.mjs "${OUTPUT_DIR}/_raw-${TIMESTAMP}.log" "${OUTPUT_DIR}"

# 清理原始文件
rm -f "${OUTPUT_DIR}/_raw-${TIMESTAMP}.log"

echo ""
echo "=== 测试完成，退出码: ${EXIT_CODE} ==="
echo "日志已写入: ${OUTPUT_DIR}/{TestClass}/${TIMESTAMP}.log"
echo "最新日志:"
ls -lt "${OUTPUT_DIR}"/*/"${TIMESTAMP}"*.log 2>/dev/null | head -5

exit ${EXIT_CODE}
```

**单独运行某个测试类：**

```bash
bash .test-output/tdd/run.sh FavoriteServiceTest
```

**为什么要脚本而不是直接 mvn test：**
- IDEA 绿色按钮跑测试时不经过 Maven Surefire 配置，日志不会落盘
- 从子目录启动时路径会错
- 脚本保证无论从哪里启动，日志都写到正确位置

### 框架配置（参考）

Maven Surefire 和 Logback 仍然配置，这样 IDE 运行时（如果配置生效）也能落盘。脚本和框架配置互为保底。

**Maven (`pom.xml`)：**

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <reportsDirectory>.test-output/tdd</reportsDirectory>
  </configuration>
</plugin>
```

**Logback (`src/test/resources/logback-test.xml`)：**

```xml
<appender name="TEST_FILE" class="ch.qos.logback.core.FileAppender">
  <file>.test-output/tdd/${testClass.name}/${timestamp}.log</file>
  <encoder>
    <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
  </encoder>
</appender>
```

### 隔离规则（强约束）

- 输出目录必须加入 `.gitignore`
- 输出目录必须加入 **当前使用的 AI 工具的忽略文件**（`.cursorignore` / `.claudeignore` / `.aiderignore` 等，按实际使用的工具配置）
- AI 默认不读输出目录
- 用户明确要求"查看 TDD 日志"时，AI 只读 `summary.json`，不读完整 `.log` 文件（除非用户指定）

## 十四、产物保护（约束）

测试代码一旦生成，进入锁定状态：

- **只增不改** — 允许追加新测试用例，禁止修改或删除已有测试用例
- **修改需特定技能** — 确需修改已有测试时，必须使用专门的修改技能（而非在开发过程中随意改动），并记录修改原因
- **锁定范围** — 测试方法签名、断言条件、测试数据均受保护；测试基础设施（Fixture、Builder、工具函数）的 refactor 不在此限制内

## 十五、完整性检查

### 15.1 覆盖检查（约束）

每条后端 BDD 场景，必须至少对应一个测试方法。有 BDD 场景但没有对应测试的，属于遗漏。

### 15.2 分层检查（约束）

每个功能接口的测试至少覆盖两层：Domain/Application 层（逻辑验证）和 API 层（接口验证）。只写了一层的，属于遗漏。

### 15.3 重复检查（规则）

检查是否有多个测试方法验证的是同一条 BDD 场景的同一个行为。如果 Given、When、Then 完全相同，保留一个即可。

### 15.4 规范检查（约束）

检查所有测试是否符合 SpringBoot 测试规范：
- 测试命名是否遵循 `{方法名}_{条件}_{预期行为}` 格式
- 是否使用了正确的分层注解
- 断言是否使用 AssertJ
