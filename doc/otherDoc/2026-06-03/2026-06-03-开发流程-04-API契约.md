# 单项目开发流程 — API 契约 / 数据结构

> 文档日期：2026-06-03
> 所属系列：单项目开发完整流程
> 阶段定位：根据后端 BDD 和前端 BDD 进行前后端接口对齐

---

## 一、核心目标

- 根据后端 BDD 和前端 BDD 的输出，定义前后端接口契约
- 多个后端/前端场景可以共享同一个接口，不是 1:1 映射
- 契约确认后，回填更新后端 BDD 和前端 BDD，将抽象的"功能接口"替换为实际接口
- 只到接口层面，不涉及更深层次的实现

---

## 二、阶段职责

### 本阶段负责（约束）

- 将后端 BDD 中的"功能接口"和前端 BDD 中的"交互动作"对齐为具体接口
- 定义接口的 URL、Method、请求结构、响应结构、错误码
- 根据项目实际情况调整接口风格
- 回填更新后端 BDD 和前端 BDD 文档

### 本阶段不负责（约束）

- 功能点识别与实体定义 → 功能点阶段
- BDD 场景编写 → BDD 场景阶段
- 后端行为场景拆解 → 后端 BDD 阶段
- 前端 UI/交互场景拆解 → 前端 BDD 阶段
- 数据库设计、技术实现方案 → 开发阶段

---

## 三、契约发现规则

### 规则 1：场景聚合

后端 BDD 中多个场景可能操作同一个功能接口，只是数据前提不同。契约定义的是接口本身，不是每条场景。

聚合方式：将操作相同功能接口、但数据前提不同的场景归到同一个契约。一个契约对应一个接口，一个接口可能覆盖多个场景。

### 规则 2：前后端对齐

后端 BDD 定义了"接口做什么"，前端 BDD 定义了"页面需要什么"。契约阶段确保：

- 后端提供的接口覆盖前端所有需要的操作
- 前端需要的每个数据都有对应的后端接口返回
- 两端对同一个操作的理解一致

对不上的地方记入待确认问题，不能假设。

### 规则 3：项目实际情况

接口设计根据项目的实际情况定义，不凭空发明风格：

- 项目已有的接口风格和规范（RESTful / RPC / GraphQL 等）
- 项目的认证方式（Token / Session / OAuth 等）
- 项目的分页、排序、筛选约定
- 项目的错误响应格式

如果项目还没有这些约定，本阶段需要先确定统一规范，再写具体契约。

### 规则 4：接口层面（约束）

契约只定义到接口层面：

- URL 和 HTTP 方法
- 请求体字段、类型、校验规则
- 响应体字段、类型
- 状态码和错误码

禁止涉及：
- 数据库表结构
- 缓存策略
- 实现逻辑
- 框架选型

出现在契约里说明越界了。

### 规则 4.1：错误码设计规范（强约束）

错误码在契约中定义，后端实现和前端处理都遵守契约，不是后端定义前端跟随。

**错误码分两层：**

| 层级 | 内容 | 说明 | 示例 |
|------|------|------|------|
| HTTP 状态码 | 语义层，通用 | 表示错误类别 | 400 / 401 / 403 / 404 / 409 / 500 |
| 业务错误码 | 精确标识具体错误 | 字符串，语义化 | `already_favorited` / `article_not_found` |

**统一错误响应结构（所有接口必须遵守）：**

```json
{
  "success": false,
  "error": {
    "code": "already_favorited",
    "message": "该文章已收藏"
  }
}
```

**HTTP 状态码使用规范：**

| 状态码 | 含义 | 使用场景 |
|--------|------|---------|
| 400 | 请求参数错误 | 字段校验失败、格式错误、必填字段缺失 |
| 401 | 未认证 | 未登录、Token 过期 |
| 403 | 无权限 | 已登录但无操作权限 |
| 404 | 资源不存在 | 查询的实体不存在 |
| 409 | 状态冲突 | 重复操作、状态不允许该操作 |
| 500 | 服务端错误 | 未预期的内部错误 |

**业务错误码命名规范：**

- 使用 `snake_case` 格式：`{实体/资源}_{错误类型}`
- 错误类型参考：`not_found` / `already_exists` / `invalid_state` / `permission_denied` / `quota_exceeded`
- 示例：`article_not_found` / `favorite_already_exists` / `user_permission_denied`

**每个接口的错误响应必须覆盖该接口的所有异常和边界场景。** 来源是 03-1 后端 BDD 中识别的异常场景。

### 规则 5：回填机制

契约确认后，必须回到后端 BDD 和前端 BDD 文档，将抽象的"功能接口"替换为具体接口引用。

替换示例：
- 后端 BDD：`对收藏功能接口发送请求` → `对 POST /api/v1/favorites 发送请求`
- 前端 BDD：`调用收藏接口` → `调用 POST /api/v1/favorites`

回填的目的是让后续的 TDD/CDD 阶段直接对照接口编写测试，无需回溯契约文档。

### 规则 6：文档驱动确认（强约束）

同后端 BDD 和前端 BDD 阶段，采用**文档驱动确认**模式。

**默认流程：**

1. AI 根据后端 BDD 和前端 BDD，一次性完成契约定义
2. 文档末尾附待确认问题清单和总结
3. 用户直接在文档中批注、修改、回答问题
4. AI 读取用户修改后的文档，继续下一轮或进入下一阶段

**主动提问的触发条件：**

- 待确认问题在文档中超过一轮未被回答
- 用户修改后引入了新的冲突或矛盾
- 发现前后端 BDD 存在对不上的地方，无法自行推断

## 四、契约模板

```
接口：{Method} {URL}
功能：{功能描述}
来源：后端 BDD {场景编号} / 前端 BDD {场景编号}

请求体（Request）:
  {字段}: {类型} — {说明} — {是否必填}

响应体（Response 200）:
  {字段}: {类型} — {说明}

错误响应:
  {状态码}: {错误码} — {说明}

Mock 数据:
  成功:     {JSON 示例}
  {错误码}:  {JSON 示例}
```

**Mock 数据要求：**

- 每个接口必须提供至少"成功"和"主要错误"两种 mock 数据
- mock 数据使用具体的值，不用 `{占位符}`
- mock 数据覆盖后端 BDD 场景中的每种数据前提组合
- 下游阶段（UI 设计、CDD、联调）直接引用这些 mock 数据，不自行编造

---

## 五、输出（约束）

API 契约阶段完成后必须产出以下内容：

### 契约列表

每个功能接口对应一份契约，多个后端场景聚合到同一个契约。

### 契约内容

每份契约包含：URL、Method、请求结构、响应结构、错误码、Mock 数据、来源场景映射。

### Mock 数据集

每个接口的 Mock 数据集，覆盖成功、各类错误、边界数据。下游阶段直接引用：

- UI 设计阶段（06-1）— HTML 原型用 mock 数据渲染各状态
- 前端 CDD 阶段（06-2）— MSW handler 用 mock 数据配置 API 响应
- 联调阶段 — 前端独立开发时用 MSW mock server 返回 mock 数据

### 回填记录

记录对后端 BDD 和前端 BDD 的修改：

- 替换了哪些"功能接口"为具体接口
- 新增了哪些接口（场景扩展带来的）
- 修改了哪些场景描述

### 总结

每次输出必须包含一份**总结**，供用户快速审核：

- 定义了多少个接口
- 聚合了多少个后端场景
- 前后端对齐了哪些操作
- 一份快速确认检查清单

### 待确认问题

文档末尾附**待确认问题清单**，每条问题包含：

- 问题描述
- 为什么需要确认
- 建议的默认选项

问题按优先级排列：前后端对不上的排前面，风格偏好排后面。

---

## 六、完成定义（约束）

满足以下所有条件后，API 契约阶段结束：

- 后端 BDD 中所有功能接口都有对应的契约
- 前端 BDD 中所有需要的操作都有对应的接口
- 每个接口都有 Mock 数据（成功 + 主要错误）
- 每份契约只到接口层面，不涉及实现细节
- 后端 BDD 和前端 BDD 已完成回填更新
- 待确认问题已全部被用户回答（或用户明确跳过）
- 总结中的检查清单已获得用户确认

---

## 七、禁止事项（约束）

API 契约阶段禁止：

- 讨论数据库表结构设计
- 讨论缓存策略和性能优化
- 讨论技术框架选型
- 讨论实现逻辑和算法
- 编写代码

这些属于开发阶段，在本阶段出现说明越界了。

---

## 八、完整性检查

### 8.1 覆盖检查（约束）

后端 BDD 中的每个功能接口，必须至少对应一个 API 契约。有功能接口但没有对应契约的，属于遗漏。

前端 BDD 中需要的每个操作，必须能找到对应的后端接口。有前端操作但没有对应接口的，属于遗漏。

### 8.2 一致性检查（约束）

同一个操作在后端 BDD 和前端 BDD 中的描述必须与契约一致。有矛盾的，以契约为准，回填修改 BDD。

### 8.3 回填检查（约束）

后端 BDD 和前端 BDD 中不应再出现抽象的"功能接口"描述，应全部替换为具体的接口引用。

## 附录：转 Skill 约束分级（注入指引）

> 本附录写给"把本文档转成 skill"的人和注入脚本看，不是流程本身的一环。
> 目的是防止转 skill 时把"方向性引导"拍平成"命令式硬约束"，导致 AI 被限制太死。

本文档的内容分两类，转 skill 注入时必须保留这个区分：

### HARD（硬约束 — 违反即流程失效，skill 必须强制卡死）

- 契约只到接口层面（URL/Method/请求/响应/状态码/错误码），禁止涉及数据库表结构 / 缓存策略 / 实现逻辑 / 框架选型
- 错误码分两层（HTTP 状态码 + 业务错误码），统一错误响应结构，业务错误码用 snake_case，每个接口的错误响应覆盖该接口所有异常和边界场景
- 后端 BDD 每个功能接口都必须对应至少一个契约；前端需要的每个操作都必须能找到对应接口
- 每个接口必须有 Mock 数据（成功 + 主要错误），用具体值不用占位符
- 契约确认后必须回填后端 BDD 和前端 BDD，把抽象"功能接口"替换为具体接口引用
- 采用文档驱动确认模式，待确认问题须全部被回答、检查清单须获用户确认
- 前后端对不上时记入待确认问题，禁止假设

### GUIDE（引导规则 — 给方向，AI 按语境自由组织，禁止固化为唯一模板）

- 接口风格（RESTful/RPC/GraphQL）、认证方式、分页排序约定按项目实际情况定，没有约定则先确定统一规范
- 四节的契约模板是参考结构，字段呈现按接口调整
- 场景聚合方式（多场景共享一个契约）是原则，怎么聚合按实际判断
- 总结和待确认问题的措辞、排列按语境组织

### 注入原则（写 skill 注入文本时遵守）

- 注入时保留 HARD / GUIDE 标记，不要把 GUIDE 类内容改写成"必须""禁止"的命令句式
- "接口风格""契约模板"这类注入时强调"按项目实际定"，不把某种风格当唯一答案
- 错误码规范属于 HARD，注入时保留完整规则；宁可注入少而精的 HARD 列表 + 一句"其余按文档精神发挥"，也不要把全文压缩成几十条命令式条款
