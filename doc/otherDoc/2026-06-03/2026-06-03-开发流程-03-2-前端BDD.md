# 单项目开发流程 — 前端 BDD（Frontend）

> 文档日期：2026-06-03
> 所属系列：单项目开发完整流程
> 阶段定位：前端关注 UI/交互状态，对应 CDD（Component Driven Development）

---

## 一、核心目标

- 将 BDD 场景拆解为前端可验证的 UI/交互场景
- 描述页面在不同状态下的 UI 表现和用户交互行为
- 驱动前端 CDD 编写组件级测试

---

## 二、阶段职责

### 本阶段负责（约束）

- 将 BDD 场景对应为前端 UI/交互场景
- 明确每个交互涉及哪个页面或组件
- 明确 UI 状态前提和预期 UI 变化
- 覆盖正向、异常、边界三种类型

### 本阶段不负责（约束）

- 功能点识别与实体定义 → 功能点阶段
- BDD 场景编写 → BDD 场景阶段
- 接口契约（请求方法、路径、参数结构、具体状态码） → Contract 阶段
- 组件代码编写 → 开发阶段
- 后端行为验证 → 后端 BDD 阶段

---

## 三、场景发现规则

前端场景的发现遵循以下规则。每条规则引导一个思考方向，规则之间不互斥——一个前端场景可能同时被多条规则触发。

### 规则 1：BDD 场景映射

每条 BDD 场景描述了用户行为，前端需要提供 UI 和交互支撑这个行为。一个 BDD 场景可能涉及多个页面或组件，每个组件的每种 UI 状态各写一条前端场景。

### 规则 2：UI 状态驱动

从页面的 UI 状态机出发，推导前端需要处理的交互场景。每个交互元素都有状态转换：Idle → Loading → Success / Error / Empty，每种状态转换路径都是前端场景的来源。

### 规则 3：边界穿透

功能点的每条边界条件，在前端都有对应的 UI 表现。不只是"数据为空"这种显式边界，还包括网络超时、并发操作、极端数据量导致渲染异常等前端特有的极端情况。

### 规则 4：前端独有关注点

以下关注点是 BDD 场景阶段不会覆盖的，前端 BDD 必须主动考虑：

- **Loading 状态** — 请求进行中的 UI 表现，交互元素是否禁用
- **网络异常** — 请求失败、超时、断网时的错误提示和补救操作
- **空状态** — 无数据时的占位展示和引导
- **重复提交** — 防抖/节流，按钮禁用期间的用户操作
- **本地状态一致性** — 乐观更新失败后的回滚
- **路由守卫** — 未登录访问受保护页面、未保存数据离开页面
- **响应式适配** — 不同屏幕尺寸下的 UI 表现差异
- **动画与过渡** — 状态切换时的视觉反馈是否正确

### 规则 5：可追溯

每条前端场景应说明其来源——来自哪条 BDD 场景的拆解、来自哪个 UI 状态的推导、来自哪条前端独有关注点。来源不明的场景需要确认其必要性，但不要求每条场景都有 BDD 场景直接对应。

### 规则 6：文档驱动确认（强约束）

本阶段与 01（功能点）和 02（BDD 场景）的讨论式推进不同，采用**文档驱动确认**模式。

**默认流程：**

1. AI 根据上游 BDD 场景，一次性完成前端场景拆解，写入文档
2. 文档末尾附**待确认问题清单**和**总结**（见输出部分）
3. 用户直接在文档中批注、修改、回答问题
4. AI 读取用户修改后的文档，继续下一轮或进入下一阶段

**主动提问的触发条件（只在以下情况打断用户）：**

- 待确认问题在文档中超过一轮未被回答
- 用户修改后引入了新的冲突或矛盾
- 发现上游 BDD 场景存在遗漏或歧义，无法自行推断

### 规则 7：场景扩展（规则）

在拆解过程中，如果发现上游 BDD 场景未覆盖的行为或风险，**直接在本文档中补充扩展场景**，不回写 BDD 文档。

**扩展场景的来源：**

- 规则 4 的前端独有关注点暴露了 BDD 场景未涉及的交互
- UI 状态机推导出了新的状态转换路径
- 边界穿透发现了 BDD 场景未描述的极端 UI 情况
- 多个 BDD 场景之间的页面跳转产生了未单独描述的路径

**扩展场景的写法：**

- 标注为"扩展场景"，与 BDD 映射场景区分
- 说明扩展来源（哪个规则触发了发现）
- 遵循与映射场景相同的质量标准（可验证、不涉及接口契约、UI 具象）

扩展场景在总结中单独列出数量，让用户快速判断是否需要将其回写到 BDD 文档。

## 四、场景拆解（规则）

每个 BDD 场景对应一个或多个前端场景。

拆解思路：BDD 场景描述了用户的什么行为，前端需要提供什么 UI 和交互来支撑这个行为，这个交互在不同状态下会有什么不同表现。

一个 BDD 场景可能涉及多个页面或组件，每个组件的每种 UI 状态各写一条前端场景。

> **关于接口引用**：本阶段涉及的后端调用使用抽象描述（如"调用收藏接口"），不涉及具体的 URL 和 HTTP 方法。API 契约阶段会根据后端 BDD 和前端 BDD 定义具体接口，并回填替换本文档中的抽象引用。

---

## 五、场景写法（规则）

每个前端场景描述一条完整路径：在什么 UI 状态前提下，用户执行什么操作，产生什么 UI 变化。

思考路径是：先确定要验证的是哪个组件的什么状态行为，然后回推需要什么 UI 状态前提，再写出预期 UI 变化。

UI 状态前提只写和当前场景直接相关的条件，不罗列与验证目标无关的页面状态。

### 场景模板

```gherkin
Feature: {功能名称} - 前端 UI/交互

  Scenario: {UI 展示场景}
    Given {页面状态}
    When 用户进入 {页面}
    Then 应显示 {UI 元素}

  Scenario: {交互正向场景}
    Given {前置 UI 状态}
    When 用户 {操作}
    Then 应 {UI 变化}
    And 应 {数据更新}

  Scenario: {交互异常场景}
    Given {异常条件}
    When 用户 {操作}
    Then 应显示 {错误提示}
    And 应提供 {补救操作}

  Scenario: {Loading 状态}
    When 用户触发 {操作}
    Then 应显示 Loading 状态
    And {交互元素} 应禁用
```

## 六、场景质量（约束）

每条场景必须满足：

- **可验证** — 每个预期 UI 变化都能写出一个组件测试来判定通过或不通过
- **不涉及接口契约** — 不出现具体的请求方法（POST/GET）、接口路径（/api/...）、具体状态码（200/400），这些由 Contract 阶段定义
- **UI 具象** — 用具体的 UI 描述，不用模糊表述（"适当的提示""正确的样式"）

做不到的，说明场景越界到了接口设计或视觉设计，需要退回到 UI/交互行为描述层面。

---

## 七、场景完整性（约束）

每个交互功能的场景必须覆盖三种类型：

- **正向** — 操作成功，UI 正确变化，数据状态正确更新
- **异常** — 操作失败，显示错误提示，提供补救操作
- **边界** — 极端条件下的 UI 表现（空数据、网络超时、并发操作、状态冲突）

三缺一，场景不完整。

正向、异常、边界是最小覆盖，不是上限。交互流程越复杂、UI 状态越多，场景就应该越多。

---

## 八、输出（约束）

前端 BDD 阶段完成后必须产出以下内容：

### 场景列表

每个 BDD 场景对应一组前端场景，每组覆盖正向、异常、边界。

### 场景内容

每个场景包含：UI 状态前提、用户操作、预期 UI 变化（成功显示什么 / 错误显示什么）。

### 覆盖映射

每条前端场景应说明其来源——来自哪条 BDD 场景的拆解（规则 1）、来自哪个 UI 状态的推导（规则 2）、来自哪条前端独有关注点（规则 4）。

### 总结

每次输出必须包含一份**总结**，供用户快速审核：

- 拆解了多少个页面/组件
- 每个组件覆盖了多少场景（正向 / 异常 / 边界各多少）
- 与上游 BDD 场景的覆盖情况（是否每条都有对应）
- 一份快速确认检查清单（用户可以直接勾选"确认"或"需修改"）

总结的目的是让用户在短时间内判断：哪些可以直接过，哪些需要仔细看，哪些需要回答问题。

### 待确认问题

文档末尾附**待确认问题清单**，每条问题包含：

- 问题描述
- 为什么需要确认（不确定点、多种可能、信息缺失）
- 建议的默认选项（如果用户不回答，AI 按此处理）

问题按优先级排列：影响场景正确性的排前面，细节偏好排后面。

---

## 九、完成定义（约束）

满足以下所有条件后，前端 BDD 阶段结束：

- 每个 BDD 场景都有对应的前端场景组
- 每组场景覆盖正向、异常、边界三种类型
- 每条场景可验证且不涉及接口契约
- 每条场景可追溯到其来源（BDD 场景、UI 状态推导、前端独有关注点）
- 无明显遗漏的边界场景
- 待确认问题已全部被用户回答（或用户明确跳过）
- 总结中的检查清单已获得用户确认

---

## 十、禁止事项（约束）

前端 BDD 阶段禁止：

- 讨论接口设计（方法、路径、参数结构）
- 讨论组件实现细节（状态管理方案、组件结构）
- 讨论技术方案和框架选型
- 编写组件代码
- 重新定义功能点和实体

这些属于其他阶段，在本阶段出现说明越界了。

---

## 十一、完整性检查

### 11.1 覆盖检查（约束）

每条 BDD 场景，必须至少对应一条前端场景。有 BDD 场景但没有对应前端场景的，属于遗漏。

同时检查规则 4 列出的每项前端独有关注点，是否都有对应的前端场景。有关注点但没有对应场景的，也属于遗漏。

### 11.2 重复检查（规则）

检查是否有多个前端场景描述的是同一条 UI 路径。如果 UI 状态前提、用户操作、预期 UI 变化完全相同，保留一个即可。

### 11.3 冲突检查（约束）

任意两个前端场景对同一个交互的预期 UI 变化出现矛盾时，必须回 BDD 场景阶段确认，不能在前端 BDD 阶段自行决定。
