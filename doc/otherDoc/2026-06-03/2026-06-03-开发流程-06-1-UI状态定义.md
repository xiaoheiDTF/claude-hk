# 单项目开发流程 — UI 设计规范 + 状态定义

> 文档日期：2026-06-03
> 所属系列：单项目开发完整流程
> 阶段定位：将前端 BDD 场景转化为可交互的 HTML 原型，用户确认后驱动 CDD

---

## 一、核心目标

- 将前端 BDD 场景转化为可交互的 HTML 原型
- 用户在浏览器中确认视觉设计、交互行为、动画效果
- 确认后的 HTML 原型作为前端 CDD 的视觉输入
- **不确认不进入 CDD** — 这是硬性卡点

---

## 二、阶段职责

### 本阶段负责（约束）

- 为每个组件生成可交互的 HTML 原型
- 原型展示组件的所有 UI 状态（Idle / Loading / Success / Error / Empty）
- 原型包含交互行为和动画/过渡效果
- 原型使用项目的实际设计规范（颜色、字体、间距）

### 本阶段不负责（约束）

- 功能点识别与实体定义 → 功能点阶段
- BDD 场景编写 → BDD 场景阶段
- 前端 BDD 场景拆解 → 前端 BDD 阶段
- 组件代码实现 → 前端 CDD 阶段
- 后端行为定义 → 后端 BDD 阶段

---

## 三、设计发现规则

### 规则 1：前端 BDD 场景映射

每条前端 BDD 场景描述了用户的交互行为，本阶段将其转化为视觉原型。

映射方式：
- BDD 的 UI 状态前提 → 原型中可切换的状态面板
- BDD 的用户操作 → 原型中可点击的交互元素
- BDD 的预期 UI 变化 → 原型中的视觉状态切换和动画

### 规则 2：项目设计规范优先（强约束）

HTML 原型必须基于项目的实际设计规范，不从零发明风格：

**如果项目已有设计规范：**
- 使用项目的 CSS 变量 / Design Token（颜色、字号、间距、圆角等）
- 使用项目的组件样式约定
- 使用项目的图标库和图片资源

**如果项目还没有设计规范：**
- 本阶段需要先确定基础设计规范，再写原型
- 基础规范至少包含：主色/辅色、字号层级、间距基数、圆角风格
- 基础规范必须经用户确认后再开始写原型

### 规则 3：可交互原型（强约束）

**每个组件生成一个独立的 HTML 文件**，用户在浏览器中直接打开确认。

每个 HTML 原型必须包含：

- **状态切换面板** — 用户可以点击切换组件的所有 UI 状态
- **交互模拟** — 按钮、输入框、下拉框等可操作
- **动画/过渡** — 状态切换时的视觉反馈（hover、click、loading 动画等）
- **响应式预览** — 展示不同屏幕尺寸下的表现（至少桌面和移动端）

原型文件命名：

```
doc/ui-prototypes/
├── BaseButton.html          # Atom 组件
├── SearchBar.html           # Molecule 组件
├── ArticleList.html         # Organism 组件
└── ArticlePage.html         # Page 组件
```

### 规则 4：标准状态覆盖（强约束）

每个交互组件的原型必须覆盖以下标准状态：

| 状态 | 说明 | 必须展示的内容 |
|------|------|------|
| Idle | 初始/未操作 | 默认 UI、所有交互元素可操作 |
| Loading | 操作进行中 | Loading 动画、交互元素禁用、进度提示 |
| Success | 操作成功 | 数据展示、成功提示、状态变更后的 UI |
| Error | 操作失败 | 错误提示、重试按钮、错误状态的颜色/图标 |
| Empty | 无数据 | 空状态占位、引导按钮、无数据提示 |

不是每个组件都有全部五个状态，但每个可能的状态都必须有原型展示。

### 规则 5：动画与过渡定义

原型中的动画和过渡必须明确，不能模糊带过：

| 动画类型 | 需要确定的参数 |
|---------|-------------|
| 状态切换过渡 | 时长（ms）、缓动函数（ease/linear/spring）、触发条件 |
| Loading 动画 | 类型（旋转/脉冲/骨架屏）、时长、是否循环 |
| 列表动画 | 进入（fade-in/slide-in）、退出（fade-out/slide-out）、是否交错 |
| 反馈动画 | hover 效果、点击反馈（缩放/抖动）、成功/失败反馈 |
| 页面转场 | 进入方向、退出方向、时长 |

在原型中用实际的 CSS animation / transition 实现，用户看到的就是最终效果。

### 规则 6：交互稳定性定义（强约束）

动画是"好看的"，稳定性是"不闪不抖不错乱"。以下场景必须在原型中明确定义行为，不能留到开发阶段自行发挥。

**过渡期间交互锁定：**

| 场景 | 定义要求 |
|------|---------|
| 按钮点击后等待响应 | 按钮立即禁用（防止重复提交），loading 期间不可再次点击 |
| 表单提交中 | 所有提交按钮禁用，输入字段可选择性禁用 |
| 列表删除动画中 | 被删除项的交互元素立即失效（不依赖动画结束） |
| 页面转场中 | 防止用户在转场过程中点击导致路由冲突 |

**最小展示时间（防闪烁）：**

| 场景 | 定义要求 |
|------|---------|
| Loading / Skeleton | 如果请求在阈值内返回（如 300ms），仍展示 loading 状态至阈值结束，避免一闪而过 |
| 成功提示（Toast） | 最少展示时长（如 1500ms），不能刚出现就消失 |
| 错误提示 | 在用户主动关闭或超时前持续展示，不能自动消失 |
| 空状态 | 数据加载完确认无数据后才展示，不能在 loading 期间闪烁空状态 |

**快速连续操作：**

| 场景 | 定义要求 |
|------|---------|
| 快速连点按钮 | 明确是防抖（debounce）还是节流（throttle），及时间窗口 |
| 快速连续输入搜索 | 明确是否延迟请求（如输入停顿 300ms 后才发请求） |
| 快速切换 Tab / 页面 | 明确是取消上一次请求，还是等待上一次完成 |

**布局稳定性：**

| 场景 | 定义要求 |
|------|---------|
| 图片加载 | 是否占位（固定宽高 / aspect-ratio），加载失败时展示什么 |
| 列表数据到达 | 逐条到达还是一次全部，到达时是否引起已有项位移 |
| 异步组件 / 懒加载 | 加载前是否保留占位空间，避免内容区塌陷后弹开 |

每条规则在原型中必须有对应的表现——用户点击"收藏"后按钮应立即变为禁用态，loading 动画不应一闪而过。不能用文字描述代替，必须可交互验证。

### 规则 7：文档驱动确认（强约束）

本阶段的确认方式和前后端 BDD 不同——**用户通过浏览器交互来确认**。

**默认流程：**

1. AI 根据前端 BDD 和项目设计规范，生成 HTML 原型文件
2. 用户在浏览器中打开每个 HTML 文件，查看和交互
3. 用户在 HTML 文件中通过批注、截图、或回复方式提出修改意见
4. AI 根据修改意见更新原型，用户再次确认

**确认维度（用户必须逐项确认）：**

- 视觉风格是否符合预期（颜色、字号、间距、圆角）
- 交互行为是否正确（按钮点击、表单提交、列表滚动）
- 动画效果是否自然（时长、缓动、过渡）
- 空状态和错误状态是否有合理引导
- 不同屏幕尺寸下是否正常

**主动提问的触发条件：**

- 原型超过一轮未被确认
- 用户修改后引入了新的组件或状态
- 发现前端 BDD 场景存在视觉歧义

### 规则 8：可追溯

每个 HTML 原型必须能追溯到前端 BDD 的场景和 Atomic Design 的组件层级：

- 原型文件名对应组件名（如 ArticleList.html → ArticleList 组件）
- 每个状态面板标注对应的前端 BDD 场景编号
- 原型中的交互行为与前端 BDD 的用户操作一一对应

## 四、原型模板

每个 HTML 原型的标准结构：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>{组件名} — UI 状态原型</title>
  <!-- 项目的 CSS 变量或 Tailwind CDN -->
  <style>
    /* 组件样式 */
    /* 状态切换动画 */
    /* 响应式适配 */
  </style>
</head>
<body>
  <!-- 状态切换控制面板 -->
  <div class="state-controls">
    <button onclick="switchState('idle')">Idle</button>
    <button onclick="switchState('loading')">Loading</button>
    <button onclick="switchState('success')">Success</button>
    <button onclick="switchState('error')">Error</button>
    <button onclick="switchState('empty')">Empty</button>
  </div>

  <!-- 组件原型区域 -->
  <div id="component-preview">
    <!-- 当前状态的组件渲染 -->
  </div>

  <!-- 对应的前端 BDD 场景映射 -->
  <div class="bdd-mapping">
    <p>Idle → BDD 场景 #{编号}: {场景名称}</p>
    <p>Loading → BDD 场景 #{编号}: {场景名称}</p>
    <p>Success → BDD 场景 #{编号}: {场景名称}</p>
    <p>Error → BDD 场景 #{编号}: {场景名称}</p>
    <p>Empty → BDD 场景 #{编号}: {场景名称}</p>
  </div>

  <script>
    function switchState(state) {
      // 切换组件到对应状态
      // 触发对应的动画/过渡
    }
  </script>
</body>
</html>
```

## 五、输出（约束）

UI 设计规范 + 状态定义阶段完成后必须产出以下内容：

### HTML 原型文件

每个组件一个 HTML 文件，展示所有 UI 状态，包含交互和动画。

### 设计规范文档（如项目尚未有）

如果项目没有设计规范，本阶段需要额外产出：

- 基础设计规范（颜色、字号、间距、圆角）
- 交互动画规范（时长、缓动、反馈方式）
- 响应式断点定义

### 覆盖映射

每个原型状态对应前端 BDD 的哪条场景，每条前端 BDD 场景都有对应的原型状态。

### 总结

每次输出必须包含一份**总结**，供用户快速审核：

- 生成了多少个 HTML 原型
- 每个原型覆盖了哪些状态
- 动画/过渡定义了多少个
- 与前端 BDD 场景的覆盖情况
- 一份快速确认检查清单

### 待确认问题

每个 HTML 原型中附**待确认问题**，用户在浏览器中查看时可见：

- 视觉不确定点（颜色选择、间距调整）
- 交互行为不确定点（动画时长、反馈方式）
- 建议的默认选项

---

## 六、完成定义（约束）

满足以下所有条件后，UI 设计规范 + 状态定义阶段结束：

- 每个前端 BDD 场景都有对应的 HTML 原型状态
- 每个组件的所有 UI 状态都在原型中展示
- 原型使用项目的实际设计规范
- 动画/过渡效果已用 CSS 实现，用户可以看到实际效果
- 交互稳定性行为已定义（过渡锁定、最小展示时间、防抖/节流、布局占位）
- **用户已逐个确认所有 HTML 原型**（确认是硬性卡点，不能默认通过）
- 待确认问题已全部被用户回答（或用户明确跳过）

---

## 七、禁止事项（约束）

本阶段禁止：

- 只输出文字描述而不生成 HTML 原型
- 使用与项目不一致的设计风格
- 省略动画/过渡的实现（用户必须看到实际效果）
- 未经用户确认就进入前端 CDD 阶段

---

## 八、产物保护（约束）

HTML 原型一旦经用户确认，进入锁定状态：

- **已确认的原型作为 CDD 的视觉标准** — CDD 阶段的组件必须还原原型中的视觉效果
- **修改需重新确认** — 如需调整已确认的视觉设计，必须更新原型并再次确认
- **锁定范围** — 颜色、字号、间距、动画参数、交互行为；文字内容和临时数据不在此限制内

---

## 九、完整性检查

### 9.1 覆盖检查（约束）

每条前端 BDD 场景，必须至少在某个 HTML 原型中有对应的状态展示。有 BDD 场景但没有对应原型状态的，属于遗漏。

### 9.2 状态完整性检查（约束）

每个组件的 HTML 原型必须展示其所有可能的 UI 状态。有状态但没有在原型中展示的，属于遗漏。

### 9.3 设计规范一致性检查（约束）

所有 HTML 原型的视觉风格必须与项目设计规范一致。出现不一致的，属于错误。

### 9.4 可交互检查（约束）

每个 HTML 原型必须能在浏览器中直接打开并交互。无法打开或无法切换状态的，属于错误。

## 附录：转 Skill 约束分级（注入指引）

> 本附录写给"把本文档转成 skill"的人和注入脚本看，不是流程本身的一环。
> 目的是防止转 skill 时把"方向性引导"拍平成"命令式硬约束"，导致 AI 被限制太死。

本文档的内容分两类，转 skill 注入时必须保留这个区分：

### HARD（硬约束 — 违反即流程失效，skill 必须强制卡死）

- 每个组件生成一个可在浏览器直接打开并交互的独立 HTML 原型，禁止只输出文字描述
- 原型必须基于项目实际设计规范，禁止用与项目不一致的风格；项目无规范则先定基础规范并经用户确认
- 每个交互组件覆盖其所有可能的标准状态（Idle/Loading/Success/Error/Empty 中适用的）
- 动画 / 过渡必须用实际 CSS 实现（用户看到的就是最终效果），禁止用文字描述代替
- 交互稳定性行为必须在原型中可交互验证（过渡锁定、最小展示时间、防抖/节流、布局占位）
- 用户必须逐个确认所有 HTML 原型，确认是硬性卡点，不确认不进 CDD
- 产物保护：已确认原型作为 CDD 视觉标准，修改需重新确认

### GUIDE（引导规则 — 给方向，AI 按语境自由组织，禁止固化为唯一模板）

- 四节的 HTML 原型模板是参考结构，怎么组织状态面板和交互按组件调整
- 不是每个组件都有全部五个状态，按组件实际可能的状态展示
- 动画参数（时长 / 缓动 / 类型）按设计意图定，规则 5 / 6 的表格是需要想到的维度清单不是固定值
- 待确认问题的呈现方式按语境组织

### 注入原则（写 skill 注入文本时遵守）

- 注入时保留 HARD / GUIDE 标记，不要把 GUIDE 类内容改写成"必须""禁止"的命令句式
- "状态覆盖""动画维度"这类注入时强调"按组件判断哪些适用"，不要求每个组件凑齐五状态
- "可交互原型""用户逐个确认"属于 HARD，注入时保留；宁可注入少而精的 HARD 列表 + 一句"其余按文档精神发挥"，也不要把全文压缩成几十条命令式条款
